# Card Studio

Official Scryfall imports offer **Maximum available (PNG preferred)**, **Large JPEG** and **Standard JPEG** image quality. Maximum keeps the native PNG when available and otherwise uses the largest supported scan, without upscaling. The single-card printing picker also has a **Download maximum-quality PNG** button for the selected face. Both faces of a double-faced card can be downloaded separately. Use **Prefer** to select newest, oldest, typical, unusual, promo, cheaper or more expensive printings, or avoid Universes Beyond; choosing a preference switches the picker to Scryfall's preferred printing. **All printings** remains available for browsing. Bulk **Populate MTG art** offers the same quality and preference controls.

In Print settings, **Card faces → Each face as a separate card** places both faces of a double-faced card in consecutive card-sized spaces on ordinary sheets. Print single-sided, cut out each face, and put both pieces in one sleeve. Copies apply to each face; single-faced cards print once per copy. This works for decks, individual saved versions and the print tray, including page ranges and individual-page PDF downloads. Generation and the library still treat a double-faced card as one card with two faces.

Studio is a local deck builder around the existing deterministic renderer. The web interface manages decks and generation jobs; the selected deck provider (Codex or Grok) researches and prepares the art/manifest; Python performs the final composition with the approved fonts and frames.

## Start

Use Node.js 22.13+ (24 recommended), Python 3.10+ and the repository's `requirements.txt` dependencies (Pillow and ReportLab). If needed:

```bash
python3 -m pip install -r requirements.txt
codex login
npm start
```

Open http://127.0.0.1:4317. No npm installation step is needed. Node may print an experimental SQLite warning; the app uses its built-in SQLite module. Stop with Ctrl+C. Run one Studio process per library.

Studio calls the `codex` executable on your terminal's PATH, reuses its existing sign-in and configuration, and uses its configured default model. A working CLI session needs image generation and web research tools. Signing in alone does not establish that those tools are available. The queue displays setup errors and blocked results rather than treating missing art as a completed card. This app does not switch to a separate image API or request a key.

The implementation uses the documented [`codex exec` noninteractive interface](https://developers.openai.com/codex/noninteractive/): JSONL events, a strict final JSON schema, and a saved output file. It starts a fresh session for each card; revisions include the previous version's image and manifest as references. The subprocess uses workspace-write with approvals disabled, and inherits your normal local tool configuration. It has the repository as its working directory. It can write within that workspace, so run this in the card project you intend to use for generation.

## Build and organise decks

1. Click **New deck**, name it, choose an optional collection, and paste a decklist. Plain lists, `1 Card Name`, `1x Card Name`, `1 x Card Name`, Arena-style `(SET) 123`, `[SET] 123`, foil tags and `SB:` lines are accepted. For example, `1 x Rin and Seri, Inseparable (sld) 1508` imports the card name without printing details. `Commander`, `Deck` and `Sideboard` headings set sections. Maybeboard is imported as sideboard. Repeated entries in the same pasted section combine quantities.
2. Leave **Start generating after import** checked to queue all unillustrated entries. One image is generated per unique entry; quantities represent copies using that image. You can uncheck it and prepare the deck first.
3. Deck details lets you edit its name, description and collection. **Style guidelines** on the deck page opens a dedicated editor for its art direction, naming and flavour rules; the same editor is visible during deck creation. A blank art direction uses `studio/default-style.txt`, a neutral fantasy brief without an animal or naming theme. The original sample deck keeps its own `card-style.txt` brief. A custom brief replaces that file for this deck. The exact effective style is saved with every job.
4. Use **Generate → Generate missing** (the deck's primary dropdown), or select cards and choose **Generate** in the floating selection bar. Selected cards can already have images: generating again makes a new version. Missing generation means missing *custom* art: it covers blank cards and cards currently showing a real MTG scan or reconstruction, which are illustrated from scratch (the scan is not passed as previous artwork; it stays in the card's version history). It skips existing custom illustrations, cards with an official scan still downloading, and already queued cards. Retrying one of those failed jobs still replaces the scan. **Generate → Regenerate all cards** queues a new version of every card in the deck after a confirmation; current art stays in each card’s version history, and cards already queued or generating are skipped. The selection bar also approves, re-frames, moves (main/commander/sideboard) or removes the selected cards; **Select all** selects every card in the current filter.
5. Open a card to change its quantity, mark it as commander, move it to the sideboard, add notes, approve it, or describe a revision. The card workshop shows the artwork and version history on the left and **Revise**, **Appearance** and **Details** tabs on the right; **Approve** and the PNG download sit in its header. Use the header arrows or ←/→ to step through the cards in the current filter. Notes save automatically. Historical versions stay available; select a thumbnail to preview it and **Use this version** to restore it.
6. Duplicate a deck from its **⋯** menu to start another collection with its current artwork. The duplicate has separate card/version records and future generations are independent. Existing image files are shared without being overwritten. Archive finished decks from the same menu and restore them from the **Archived** toggle on My decks.
7. **Print & export** offers the print PDF and an export of the decklist or a ZIP containing `decklist.txt`, deck metadata and one current PNG per illustrated entry. Individual PNG downloads are available in the card workshop.

The deck page header has five controls: **Add** (paste cards, basic lands, tokens, card art variants), **Style** (the deck's style guidelines), **Print & export**, a **⋯** menu (deck details, card frame, which image provider illustrates new cards, refresh card data, duplicate, archive) and the primary **Generate** dropdown (**Generate missing**, **Regenerate all cards**). While this deck has cards generating, the button shows a spinner with the count, and its dropdown adds **View generation queue** and **Cancel generation**. Below the summary, the **Cards** and **Analysis** tabs separate browsing from deck-building statistics. The card toolbar has search, a status filter, a **Filters** popover (type, colour, mana value, role), sort, **Preview** and view controls; active filters appear as removable chips.

**Full-screen preview:** click **Preview** in the toolbar, the expand button on a card's corner, or the artwork in an open card to see the full card as large as the window allows. Use **←/→** to move through the cards currently shown (filters and sort apply), **Home/End** for the first/last card, **F** to flip double-faced cards, **Enter** or **Card details** to open the card's workshop, and **Esc** to close. On touch screens, swipe left or right.

Invalid import lines are reported together; the import makes no changes until they pass. Card names are verified by the selected provider during generation, so import does not establish that every name exists. Counts and type summaries support deck organisation; the building checks flag common Commander issues without claiming a complete legality check. Type summaries use independent card metadata when available, and saved card manifests otherwise. Planeswalkers, tokens and paired transform/modal faces have dedicated support. Saga, Class, Battle and split structures still require additional dedicated templates. Adventure and prepare cards use dedicated same-side inset spells.

**Skip cards already in this deck** is enabled by default when creating decks and adding cards. Re-pasting a full list preserves existing entries, quantities, notes and versions. Matching is case-insensitive, normalises whitespace and apostrophes, and ignores the printing details removed by the parser. A commander already in the deck is also recognised when pasted in an unsectioned main list. Explicit main/sideboard entries remain separate. Misspelled names are accepted as input, but are not guessed to be the same card during de-duplication.

**Add → Replace deck list…** swaps the whole list. Paste the complete new list and choose **Preview changes** to see what will be kept, added, removed (flagging removed cards that have artwork) and changed; **Replace deck list** then applies it in one step. Cards that stay keep their card record: artwork, version history, notes, appearance controls, approval and role tags. Their quantities and sections follow the new list, so a card moved to the sideboard keeps its art. Matching uses the same name rules as import, including either face of a transform/modal card. If the new list has no Commander heading, an existing commander listed in the main deck stays commander; with a Commander heading, the sections are taken as written. Art variants of one card keep their illustrations, and their copies are fitted to the new total: the last variant grows, shrinking reduces variants from the end down to one copy each, and only then are trailing variants removed. Tokens not in the list are kept unless you untick **Keep tokens that aren’t in the list**; new tokens still need **Add → Tokens**. Cards with queued or running generation must be cancelled before they can be removed. Removed cards leave the deck with their version records, but their image files stay on disk. Newly added cards start without art; use **Generate → Generate missing** to illustrate them.

De-duplication only checks the current deck. New decks and newly added cards start without artwork, even when the same Magic card has been illustrated elsewhere. Turn de-duplication off to add quantities to existing entries. To reuse an illustration deliberately, open the card workshop and choose **Choose artwork**. The gallery shows matching versions from other decks, with deck filters and paired-face previews. Selecting one copies the art into an independent version, applies the destination deck’s frame and explicit card controls, and preserves the source. Existing destination names/flavour are retained; a card with no existing version uses its original Magic name and no imported custom flavour by default. The source deck’s theme is never inferred. Source provenance is saved in `reuse.json`. Duplicating an entire deck still intentionally copies its selected versions.

## Build the deck before generating art

The integrated **Deck analysis** panel shows quantity-weighted card types, mana curve, average nonland mana value, coloured mana pips, land sources, sideboard totals and estimated deck roles. Multi-type cards appear in multiple type counts. Multi-face cards use the front face for type and mana-cost display. Role estimates use simple rules-text patterns; set your own comma-separated tags to replace them for a card.

The app looks up card data on first opening an imported deck and after adding cards, independently of art generation. **Refresh card data** requests fresh metadata from Scryfall; names it cannot resolve are shown for correction. The server uses the [Scryfall collection endpoint](https://scryfall.com/docs/api/cards/collection), batches up to 75 identifiers, and caches responses in SQLite. Lookup failure leaves the deck usable and does not mark artwork as generated. Live lookup was not available for verification in this sandbox; the request/response flow is covered by fixtures.

On the **Analysis** tab, click a type, mana-curve bar or role count to filter the cards; this returns to the Cards tab with the filter applied. Search names, rules and roles; sort by name, mana value, type or quantity. Switch to list view to edit copies, commander/main/sideboard sections and role tags directly, or remove entries. The Commander checks cover deck size, repeated nonbasic names, colour-identity mismatches and available Scryfall legality status. They do not establish partner/companion eligibility, exception text or full legality. The [official Commander overview](https://magic.wizards.com/en/formats/commander) explains the format.

## Card appearance and history

Open a card and use its **Appearance** tab:

- Title: follow the deck style, keep the original Magic name, or enter an exact alternate title.
- Flavour: follow the deck style, omit it, or enter your own wording.
- Rarity: original rarity, common, uncommon, rare or mythic. This changes the printed expansion-mark colour.
- Crop: optional horizontal/vertical art-focus percentages. Focus affects only axes that need cropping.

**Save controls** sets choices for future jobs. **Apply as new version** recomposes the current saved artwork locally without calling Codex or generating new art. The trusted renderer applies explicit choices after generation, so exact titles/flavour and rarity are enforced rather than left to the image model. Full rules and readability constraints still apply; text that cannot fit fails without replacing the current card.

Each version retains its image, manifest, build report, scene description, effective style and appearance choices. The base `source-manifest.json` preserves values before explicit appearance overrides, allowing reset to original rarity or style-derived text. Selecting **Use this version** restores that image and its saved controls. Review approval resets. Changing the deck’s style affects newly queued jobs; existing images and already queued style snapshots stay intact. Old imported cards may lack some historical fields; the original sample style and scene descriptors have been imported explicitly.

## Tokens and multiple illustrations

**Tokens / art variants** adds token entries, basic-land variants or variants of another named card. Choose the number of unique illustrations and total physical copies. Counts are distributed evenly: 20 Forests with ten illustrations becomes ten entries with two copies each; six illustrations and six copies produces six distinct images. Existing ungrouped copies can be split while preserving their total, existing first image, notes and history. Additional variants always bypass artwork reuse/de-duplication. Re-pasting the complete decklist preserves those variants.

Token presets include the 1/1 green Cat and 1/1 white Dog created by Rin and Seri. Expand **Customise token details** for other types, colours, stats and rules. Definitions are explicit user-defined token specifications, not guessed ordinary cards named Cat or Dog. The compositor enforces them and prints no mana cost. Tokens have a separate section and do not count toward the main deck, mana curve or singleton checks. Choose **Include tokens** in print settings to include/exclude them. Each variant has independent art, saved scene descriptors and version history. Duplicate-art checks compare files and decoded pixels. Scene similarity includes same-name variants.

## Frame Studio

Open **Card frames** (under *Card design* in the sidebar) to create named frame sets independently of decks. The page works like **My decks**: each frame shows a fan of its five mono-colour previews, **What every frame covers** lists the required card types, and **New frame** or the dashed tile starts a design. Describe the desired materials, palette, borders, panel transparency and ornaments, then start a Codex frame-design job. Generated data is declarative JSON; generated executable code and AI-painted text are not used. Real bundled fonts and measured text anchors remain consistent. Every set requires previews for all thirteen supported standard structures, all base colour palettes, and automatic multicolour/legendary treatment. It becomes selectable only after trusted validation checks coverage, text fit, contrast and ornament placement. Review the proof matrix and individual layout previews. In the editor, **Variant → Real artwork** replaces the placeholder in the live proof with a random generated custom illustration of a matching card type from any deck (creature art for Creature, saga art for Saga, back-face art for Transform back). Structures nobody has illustrated yet borrow creature or enchantment art and say so. **Shuffle** picks another. Official and reconstructed scans are never used, and annotated generation references keep the placeholder.

**Template library** (the dashed tile on the Card frames page) lists the Magic Set Editor Full Magic Pack templates, which are printed-style frames drawn by Magic Set Editor with the official fonts. Filter by era, search, and by default show only print-quality (250+ PPI) frame art. **Use this frame** adds a template as a frame set, rendering every card type in a few minutes. Template sets are not regenerated or edited; choose another template instead. See `docs/mse-templates.md`.

**Design inspiration** in the new-frame dialog and the editor’s **Frame settings** lets you select a deck artwork set, including one that is currently inactive. Keep writing a **Design brief** to specify the frame you want. The designer combines that prompt with the selected set’s effective style guide, pinned reusable style and reference images. It inspects illustrated commanders first, then representative card art, with access to the selected versions of every card and both faces where applicable. Only custom illustrations are used as card-art references; official scans are excluded. Sets without illustrations use their style guide. **Standalone prompt** keeps the original prompt-only workflow. Choosing inspiration does not switch the deck’s active artwork set or apply the resulting frame to it. Each job saves its style snapshot and selected card-version/art paths in `request.json` and `deck-style.txt`; later style or artwork-set changes do not alter that queued request. The inspiration choice persists for future frame revisions.

**Flavour** (in the frame options) sets how far the design departs from a printed card: **Classic** (printed-Magic restraint; the art carries the card), **Stylised** (the theme is recognisable from the frame alone, using at least two themed elements such as a bar shape, double/pinstripe/foil rails, motif symbols, textures or painted decorations) or **Showcase** (painted decorations, textured panels and a strong signature motif). **Designer’s choice** infers it from the brief. Optional **Brief details** (motifs, materials, signature element, palette, things to avoid) are saved with the set as `brief_fields` and passed to the designer as binding ingredients.

**Design 3 options** (on by default in the new-frame dialog and beside **Generate new version**) queues three designer jobs in parallel from the same brief and real-art proofs. Left to right: **Simpler** (one flavour level lower, closer to a classic frame), **Your brief** (as written) and **More flavour** (one level higher). With Designer’s choice the sides are relative to the designer's reading of the brief. The frame page shows the latest group under **Choose your favourite**: each option's real-artwork proofs, its concept name and signature element, and its closest existing frame set. **Use this one** makes it current; **Preview** loads it in the editor. Until you choose, the *Your brief* option becomes current when ready. Each option is an ordinary validated version, so the others remain in the version menu. Uncheck the option to generate a single version.

Every designer job first writes `concept.json` (two or three distinct concepts and the chosen one, whose flavour level must match the option's target). `studio/verify_template.py` then runs a design review (`studio/frame_review.py`, saved as `design-review.json`): it checks that the requested flavour level is actually delivered, checks that the options of one run look clearly different from each other (frames are not compared with your other saved sets), measures lettering contrast on the rendered pixels, and renders `previews/real-art-proofs.jpg` with real illustrations from the inspiration deck (commander first) or random library art. As on printed Magic cards, the illustration stays clear: ornaments and painted decorations must sit on the frame (bar ends and edges, rails, the stats box, crest or border), and the review rejects any item more than 10% off the frame. Each new frame set also designs its own vector **rarity symbol**, which the renderer colours black, silver, gold or orange-red by rarity; the real-art proofs cycle through the rarities so you can see each. When a bar shape cuts into its ends (ticket notches, swallowtails, scallops, deep steps), the title, type line, mana cost and rarity symbol move inward by the measured depth so lettering keeps a plain bar's clearance. The designer's vocabulary (bar shapes, rail styles and finishes, panel textures, per-surface text colours, motif symbols, tinted decorations and full-card overlays) is documented in `docs/frame-schema.md`; `examples/frame-sets/` has deliberately different classic, art-deco and showcase examples.

Frame sets retain versions and can be refined with a new brief; earlier validated versions can be reactivated. Choose a frame on a deck with **⋯ → Card frame**. The dialog previews the chosen frame on the deck’s own artwork: one illustrated custom card for each colour palette in the selected artwork set (each mono colour, the most common multicolour palette and colourless), plus a legendary card, preferring the commander. Previews are transient recompositions with the deck’s outer border; no versions are saved. **Current cards** switches the tiles to the cards as they are now for comparison. The wider dialog shows large cards backed by 900 px preview images. Artwork stays visible while a replacement frame loads, and switching away cancels obsolete native renders and skips obsolete queued work. MSE samples are prefetched as one batch and use one composed-card export per stylesheet, without producing unused transparent overlays. Outer borders are applied in the same preview worker. Previews are cached in `library/frame-preview-cache`, with artwork, frame and border changes included in the cache key; returning to an unchanged frame reuses the images. Every newly queued card job saves a copy of the exact set version. **Apply to all current cards** in that dialog, or **Apply frame** in the selection bar for selected cards, creates new versions using existing artwork without new image generation. Historical card images remain intact. The included set is named **Bloomburrow inspired** and is the initial default. Sets can be renamed, and any validated set can become the default for newly created decks; existing decks retain their selection. Click a set to open its full-size detail page. The JSON example is `examples/frame-set.json`.

## Planeswalkers and double-faced cards

Planeswalkers render loyalty costs in individual shields beside ability rows, plus starting loyalty at the bottom right. Transform/modal cards retain two complete face objects and separate artwork. The workshop provides Front/Back controls, per-face appearance overrides and face downloads; ZIPs contain both sides. A paired version restores both faces and their controls together. Unsupported structures still fail explicitly rather than flattening required gameplay.

## Rate-limit recovery

Rate-limit, HTTP 429 and usage-limit failures keep the card queued. Studio uses an explicit retry/reset time when present, otherwise exponential delays starting at 30 seconds and capped at 30 minutes. Independent Codex and Grok cooldowns prevent waiting workers from hammering the same provider; the other provider can continue. Up to eight automatic retries are attempted, with attempt files in separate directories; persistent limits then become a clearly reported manual-retry failure. Limits/reset times are parsed best-effort from the selected provider’s error messages. The queue displays its next retry time. Completed versions are never replaced by failed attempts.

## Print the deck

Choose **Print & export → Print PDF** on a deck. Choose A4, Letter, A3 or custom paper, orientation, card width/height, margins, spacing, bleed, image quality, crop marks and an optional calibration page. Include quantities or print one of each entry; optionally include the sideboard or skip unillustrated entries. A sheet diagram shows layout and page count before downloading.

Default trim size is **63.5 × 88.9 mm** (2.5 × 3.5 inches); A4 with 5 mm margins, 2 mm spacing and no bleed fits nine cards per sheet. Letter needs margins around 4 mm to fit nine at that trim size. Bleed reduces available slots. Crop marks require at least 0.5 mm spacing. The exporter rejects impossible layouts, more than 1,000 copies, and missing images unless explicitly skipped.

PDFs contain current selected fronts, double-faced backs, or paired duplex pages, with quantities expanded, exact physical dimensions, and RGB images. Full resolution preserves native source pixels; explicit 600 and 1200 PPI options resize to the chosen output resolution, and compact uses 300 PPI. Nonmatching image aspect ratios are padded to preserve all card content. Bleed extends edge pixels outside the trim and does not enlarge or crop the printed face. Historical originals are untouched. The optional calibration page includes a 100 mm test square.

Choose **Download format → Individual PDFs · page links + ZIP** to export each sheet as a separate single-page PDF without reducing image quality. After choosing **Prepare print files**, use **Open & print** to open one sheet in the browser, then Ctrl+P and Actual size / 100%. Each sheet also has a **Download** link for another PDF reader. The complete ZIP is optional. Completed exports have a standalone page list that can be bookmarked and reopened without regeneration. The print modal also remembers the last completed export and print settings for each artwork set and card selection. Reopen it to see saved page/download links immediately when the selected versions, quantities, source files, borders and print layout still match. Changed inputs hide the saved links until a new export is prepared. Preparing identical inputs reuses the completed files. History survives browser refreshes and Studio restarts. Downloads stream directly to the browser download manager instead of buffering the whole file in JavaScript. Files retain their original page numbers, including selected page ranges; paired duplex pages are labelled front/back and the calibration page is separate. This avoids opening an entire deck in one PDF viewer. Image preparation and separate-page PDF creation use up to four worker processes, limited by available memory. Prepared lossless image streams are cached in the library’s `exports/print-cache` directory and reused on later exports; changing source images, output resolution, trim size or bleed creates new cache entries. Pages reuse these streams directly rather than encoding temporary PNGs and compressing them again. For automatic duplex printing, use **One combined PDF**; separate front/back files require manual pairing.

Print using **Actual size / 100%**, disable Fit to page, and check the calibration square before a full run. Adjust paper, trim/bleed and colour conversion to your printer's specifications. For paired duplex output, choose long-edge or short-edge mirroring to match the printer. Only double-faced entries provide a back image; other slots stay blank. Test alignment before a large run. The exporter does not perform printer-specific CMYK conversion. ZIP exports remain available for services that want individual fronts.

## Composition variety

Every fresh card job receives a persistent, balanced scene-plan starting point. Plans vary distance, viewpoint, placement, actions and setting ideas. When a queued job starts, Studio refreshes its references to cards completed earlier in the deck, including earlier jobs from the same batch. The agent inspects relevant images and saves `scene.json` with distance, viewpoint, subject position, pose/action/setting/lighting keywords and a factual summary.

`node studio/check-scene.mjs REQUEST.json SCENE.json` compares descriptors before art generation and after visual review. Similarity weights position 16%, viewpoint 15%, distance 15%, pose 25%, action 15%, setting 10% and lighting 4%; keyword overlaps use Jaccard similarity with a small synonym map. Pairs scoring at least 68% with overlapping pose tags are flagged. At 78% or above, a fresh composition fails acceptance until it is changed. Cosmetic recompositions and revisions that explicitly preserve the prior scene do not force new art.

The deck’s **Composition variety** section lists near-matches; each card version exposes its saved scene keywords. The eight original samples have manually reviewed descriptors in `data/sample-scenes.json`, including the repeated left-side cats identified by the user. The cat-and-dog brief includes that feedback. Existing illustrations are preserved for review. These static checks compare self-reported descriptions, not image embeddings or an independent vision classifier, so visual review remains necessary.

## Queue and revision behaviour

Choose **Codex workers** and **Grok workers** in the queue to run 1–4 card jobs per provider across decks. Each setting persists independently; reducing a limit lets its already running jobs finish. Two per provider allows four simultaneous AI card jobs. Frame design jobs run separately and share the Codex account and its provider-specific rate-limit cooldown. You can close the browser while Studio continues working. The queue shows progress, failures, retry and cancel controls. **Pause queue** prevents another job from starting; the current job continues. Cancel stops the current process group on Linux/macOS or removes waiting work. Existing card versions stay available while revisions run. A successful job becomes the current version and resets review status.

Every job has its own directory:

```text
library/
  studio.sqlite
  decks/<deck-id>/cards/<card-id>/versions/<version-id>/
    request.json
    style.txt
    codex-prompt.txt
    events.jsonl
    result.json
    manifest.json
    ...saved art, lookup snapshots and prompts...
    rendered/<card-id>.png
    rendered/<card-id>.frame.png
    rendered/<card-id>.report.json
  exports/
```

`request.json` records the selected card, per-card notes, deck context, revision request, previous version and output paths. The job prompt directs Codex to use the local card-making skill, preserve gameplay and approved geometry, keep all new files inside this version directory, and return a one-card manifest. The server checks scene variety and the returned path, then rebuilds the card through `studio/verify_result.py`. A job succeeds only after real artwork and a valid manifest pass the renderer and its output artifacts are saved.

The trusted rebuild validates the existing renderer's schema, layout and artwork requirements. It does not independently prove that Codex's card transcription matches current Oracle text; research snapshots and visual review remain part of the card skill. Image generation itself is not deterministic; composition from the saved art, manifest and fonts is.

Queued jobs survive restarts. An interrupted running job becomes a retryable failure; graceful shutdown cancels it. Retry creates a fresh version directory. Failed/cancelled attempts never replace a current card image. Jobs have a one-hour time limit. A provider that produces no output at all for 5 minutes (Grok, which streams its reasoning) or 10 minutes (Codex) is treated as a stalled stream: Studio stops it and retries in a fresh attempt directory, up to two times, without setting a rate-limit cooldown. Grok jobs also report each reasoning phase in the queue, so long thinking stays visible. Removing a card removes its database records; its files are left on disk. Archiving preserves the complete deck.

Back up `library/` with Studio stopped, plus the project's `art/`, `decks/` and `output/` directories for the original imported examples. The SQLite database stores absolute asset paths; moving the whole project requires migrating those paths. An export ZIP is a portable collection of current card images, not a full history backup.

## Configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `4317` | Local HTTP port |
| `CODEX_BIN` | `codex` | Path to the Codex executable |
| `CARDFORGE_PYTHON` | `python3` | Python executable with Pillow installed |
| `CARD_STUDIO_STALL_MINUTES` | 5 (Grok) / 10 (Codex) | Minutes of silent provider output before a job is stopped and retried as stalled |
| `CARD_STUDIO_LIBRARY` | `<project>/library` | Persistent library directory; use a directory inside this project so workspace-write jobs can save their files |

The server binds to `127.0.0.1`, checks its Host header and mutation origin, and requires a per-process request token for writes. It serves database-selected artifacts under the project/library, not arbitrary user-supplied paths. Do not expose it as a public website. Authentication is handled by the local Codex installation; Studio never reads or copies credential files.

## Development and verification

```bash
npm run dev
npm run test:studio
python3 -m unittest discover -s tests -v
```

There are no frontend build steps or npm dependencies. `studio/server.mjs` serves the plain JavaScript/CSS interface, dispatches API requests and streams change notifications. `store.mjs` owns SQLite persistence; `metadata.mjs` fetches builder metadata; `printing.mjs` and `print_deck.py` produce print PDFs; `public/scenes.js` compares composition descriptors; `decklist.mjs` handles imports; `runner.mjs` owns the parallel Codex queue and subprocess lifecycle.

Tests exercise the real HTTP request listener in memory, so no port is needed. A synthetic Codex executable emits the JSONL/final-result protocol; the real Python renderer composes and verifies its output. Other checks cover cross-deck isolation, atomic imports, local request guards, restart recovery, cancellation, history, rollback, exports and interface rendering/escaping. The fixture is test-only and never selected by the application.

The original restricted sandbox denied browser/server startup; after permissions were expanded, live localhost operation and isolated Chrome workflows were checked. Card generation is now running through the local signed-in Codex CLI. Automated frame-design tests use a synthetic protocol fixture to avoid spending account usage. Run the following final smoke check in a normal local terminal: start Studio, inspect the sample gallery, create a one-card deck containing Sol Ring, generate it, request a small revision, and switch back to version 1.


Frame controls include bordered inset artwork or borderless artwork, fitted or full-height rules panels, legendary crests, material rails and title/type/subtitle padding. Explicit choices are enforced by the trusted renderer after the designer produces its configuration. Copper, gold and silver material rails remain consistent across all card colours; inner accents indicate colour identity. Every version includes a matrix of 34 colour/legendary combinations and thirteen structure proofs. The detail page can render any combination at full resolution, including alternate titles.

Real printed-card reference photos are cached under `assets/frame-references` with artist and source links. Refresh with `node studio/fetch_frame_references.mjs`. Adventure and prepare references inform supported inset layouts. Saga and Battle examples remain visual references for structures that still require dedicated renderers. Reference photos preserve their printed credits; custom rendered cards remain footer-free.

The frame detail page has **Editor** and **Overview & references** tabs, plus a version menu in its heading for previewing or reactivating any validated version. The editor has three panes: preview context on the left (card structure, colour swatches, legendary and alternate-title variants), the live proof sized to the window in the centre, and a tabbed inspector on the right (**Selection** measurements, change **Notes**, and **Set settings** for the name, brief and design options). A sticky bar shows unsaved changes with **Save settings** and **Generate new version**. **Edit layout** is the default tool; **Clean preview** hides the guides. **Edit layout** lets you drag the title bar or type/rules boundary vertically and resize the title, type and attached original-name tab using their square handles. Numeric padding remains available for precision; arrow keys move a selected bar, with Shift for larger steps. Geometry is constrained by text fit, attached subtitles and fixed horizontal anchors. Handles update immediately; a debounced trusted Python render refreshes the actual card without invoking Codex. Invalid spacing reports an error and retains the last valid proof.

Undo/redo and local browser drafts protect work in progress. **Save settings** stores the measurements and annotations in the set; **Generate new version** freezes them into the revision request alongside its selected source version. The backend produces numbered annotated reference PNGs and `visual-edits.json`, then gives them to the frame designer. Explicit measurements remain enforced by the trusted verifier. Older frame and card versions are not edited.

The deck's **Add** menu has **Paste cards**, **Basic lands**, **Tokens** and **Card art variants**. Basic lands and tokens open their respective entry forms directly, including unique illustration and total-copy counts. **Card art variants** opens the matching workflow for ordinary cards. The dedicated add-land flow adds copies by default; splitting existing copies remains optional.

On creature and token frame previews, **Edit layout → Power / toughness** selects the statistics box. Drag it horizontally or vertically, or drag its corner to resize width and height. Left/top/width/height inputs allow exact measurements. The renderer centres the real-font statistics inside the resulting box and retains the readability floor. Bounds keep it in the lower card area, outside rules text. These measurements are included in saved controls, annotated references and generated revisions, like the other frame edits.

## Reusable Styles and reference analysis

**Art styles** in the sidebar is a library of versioned art-technique prompts, laid out like **My decks** with an Active/Archived toggle, search and a **New art style** button. Starter entries are Painterly Gouache, Ink & Watercolour, and Cinematic Digital Painting. Create, rename, edit, duplicate or archive entries; earlier revisions can be selected again. Styles describe medium, mark-making, texture, rendering and colour treatment. Subjects, character identities, worlds, scenes and camera framing belong to the deck guidelines.

**Style guidelines** on a deck opens a full-page editor. Select a reusable Style and pin its revision, or choose **Use the deck prompt**. A chosen Style controls art technique when it conflicts with deck text. **Custom prompt** preserves the complete freeform brief, including the existing Friends of the Forest prompt. **Structured sections** stores separate art-style, composition, character, world, lighting, palette and naming/flavour fields. Switching modes preserves both representations. New decks can select a Style at creation. Updating a library Style does not automatically update decks; its linked-deck controls apply the current revision only to decks you select.

Upload PNG, JPEG or WebP reference images by file picker or drag-and-drop (up to 12 images, 12 MB each, 36 megapixels). Originals are retained alongside normalized analysis images and thumbnails. Select reference thumbnails, add optional extraction notes, and choose **Analyse selected references**. Style-library analysis extracts art technique only. Deck analysis uses selected feature checkboxes and returns separate editable sections. The worker attaches the images to the local Codex CLI and uses a structured result schema. It does not generate images or require a separate API key.

Proposals do not change prompts automatically. Review/edit the returned fields and apply explicitly. Structured deck application merges only selected sections; custom application appends labelled sections to the current raw prompt. Current unsaved editor values are saved before analysis/application so unselected edits are preserved. Applied proposals remain in history. Failed tasks offer retry/cancel, survive restarts and share the Codex provider’s rate/capacity cooldown, with separate attempt artifacts.

Every new card job saves its effective `style.txt`, `art-direction.json`, pinned Style revision and copies of relevant reference images. Style references are scoped to technique; accepted deck references carry their selected feature scopes. Uploaded deck photos do not influence card generation until an extraction is applied. Old card versions and already queued work retain their previous snapshots. Recomposition retains its earlier style text and artwork. Removing a reference hides it from new selection while preserving images used by saved revisions or jobs. Deck duplication copies the selected Style revision, guideline sections and deck-reference associations.

Storage: `art_styles`, `art_style_revisions`, `art_references` and `style_extractions` in SQLite; uploads in `library/art-references/`; extraction requests, image snapshots, prompts and results in `library/style-extractions/`. These art-technique templates are independent of Frame Studio's deterministic card-frame sets.


Names such as `Bala Ged Recovery // Bala Ged Sanctuary` import as one entry. Metadata collection lookups use the front name, retain the full Scryfall `card_faces` record, and use an exact named fallback when needed. Front and combined names de-duplicate as the same card; known back-face aliases are cached and recognised. The workshop can show front/back gameplay data before artwork exists. Transform and modal double-faced cards require two independent face illustrations and export front/back images; Adventure and prepare cards have one physical face and one art file, with their secondary spell preserved in `spell`. Adventure insets appear on the left; prepare insets appear on the right. Both spell costs, names, types and Oracle texts remain separate and complete. `data/` retains current Scryfall snapshots for Bala Ged Recovery, Bonecrusher Giant and Emeritus of Ideation.

## Hybrid frame materials

Frame Studio combines measured panels and real-font lettering with optional frozen transparent PNG ornaments. Organic fluid, carved materials and intricate filigree can be generated as artwork; title/type/rules panels, mana symbols and gameplay remain deterministic. PNGs are masked away from text and statistics. Each ready version retains its assets and prompts, and each card job copies its own hashed asset snapshot. Earlier frames and cards remain unchanged.

Backend integration: POST /api/frame-sets/:id/generate accepts optional decoration_inputs, up to eight objects with a local project PNG path, role and source prompt. The worker copies these into the new version's inputs directory and instructs the designer to reuse them. This supports already approved ornament assets alongside normal agent-generated designs. Ordinary generation can create suitable transparent details through the built-in image-generation tool.

Config decorations is an array of image (relative PNG path), box [x0,y0,x1,y1] on the 1500×2100 canvas, fit (contain/stretch), optional mirror_x, opacity, layer (under/over), layouts and legendary filters. Load configs through cardforge.decorations.load_set so relative paths and recorded hashes are verified. The verifier requires genuine RGBA transparency, bounds and asset limits; snapshots are self-contained. These are frame material controls, separate from reusable illustration Styles.


Deck headers show **Cancel generation** beside Generate whenever that deck has queued or running card jobs. It cancels both states for the current deck, including pending automatic retries, and terminates its active worker processes. Completed versions and other decks are preserved. The operation is idempotent: POST /api/decks/:id/cancel-generation returns cancelled, queued and running counts.

New compositions default to content-fitted rules panels capped at 40% of card height, including the type bar. Body text scales from 64px down to a hard 36px floor before reporting overflow. Frame Studio can explicitly retain Full height, subject to the same cap. Existing saved images stay unchanged; recompose/apply frame creates a new version using the current layout.


## Image provider per deck

Use **Generation provider** beside the deck generation controls (also in Deck details) to choose **Codex · GPT** or **Grok · subscription CLI**. The choice belongs to the deck and applies to new illustrations and revisions of existing cards. Every job pins its provider in request.json; changing the deck does not rewrite already queued jobs. A new generation/revision uses the currently selected provider even when earlier artwork came from another provider. Previous versions remain available; a revision can pass the previous raw artwork as an edit reference. Applying a frame reuses saved art without contacting either image provider.

To override the deck for one card, open it and choose **Generate with** on its **Revise** tab. **Deck default** follows the deck's provider; choosing Codex or Grok makes that card use it for every new generation or revision, including ones queued from **Generate missing**, **Regenerate all** or a selection. Overridden cards show “→ Grok” or “→ Codex” beside their version label in the grid. The override is saved on the card, copied by deck duplication and art-variant splitting, and, like the deck setting, does not rewrite already queued jobs.

Each version records which AI made its artwork (`art_provider`). It is shown in the workshop's version history, under the selected version, in the fullscreen viewer, beside the version label in the grid, and on generation queue entries. Appearance and frame updates, artwork chosen from another deck, and duplicated decks keep the provider of the art they reuse. Older versions were backfilled from their saved job requests; versions with no job record (such as the original style studies) show no provider.

Install Grok in WSL using the official installer, then run `grok login --device-auth` and complete the browser sign-in. The app discovers `~/.grok/bin/grok` or GROK_BIN. GROK_HOME can select its credential/session directory. The CLI integration removes XAI_API_KEY from its subprocess and sets GROK_DISABLE_API_KEY_AUTH=true. It uses the official built-in image_gen/image_edit tools with your cached login, subject to subscription eligibility and quotas; no direct inference API or paid API fallback is implemented.

For Grok decks, the runner launches the signed-in Grok CLI directly for the **entire** card job: research, interpreting guidelines, scene design, custom names/flavour, image generation/editing, review, manifest and composition checks. It never launches Codex and does not use a nested image agent to rewrite the prompt. Grok calls its own image_gen/image_edit tools directly, copies the original source into the job, and runs the shared prepare_grok_art.py utility for recorded print-size preparation. Native resolution and upscaling remain in provenance. Grok must write result.json before finishing; the same trusted renderer and scene/version validation then apply. Its events and prompt are saved as events.jsonl and grok-prompt.txt.

Codex decks continue to run entirely through Codex and its built-in image tools. Neither provider falls back to the other on failure. Applying a frame or cosmetic controls runs locally without either agent. Provider choice is frozen per job, while new generations and revisions use the card's override or, without one, the deck's current choice. Authentication remains in each CLI's own credential store.



The **Refine this card** field is optional. Leaving it blank (including whitespace) creates a new illustration using the deck's current guidelines, pinned reusable Style, selected image provider, frame and saved appearance controls. Earlier versions remain unchanged. Providing refinement text instead applies those specific changes to the previous version.


## Independent provider cooldowns

Codex and Grok rate-limit cooldowns are separate. The scheduler skips waiting jobs for a limited provider and fills available worker slots with eligible jobs from the other provider. Jobs retain their frozen provider even when a deck's setting changes. Cooldowns persist in queue_provider_cooldowns; jobs index their saved choice in generation_provider. Legacy queued choices are recovered from request.json, and legacy reset dates are attributed to the corresponding provider. The queue shows each limited provider and its retry time separately. Worker limits are also independent: each provider has its own 1–4 slots. Local recomposition uses a separate single worker.

Frame Studio and reference-analysis workers currently use Codex and share only its cooldown. Local frame/text recomposition requires neither AI provider and bypasses both cooldowns. Automatic retries retain their provider and attempt history.


POST /api/queue accepts {provider: "codex" | "grok-cli", concurrency: 1..4} to change one provider. Omitting provider updates both limits for compatibility. Bootstrap and queue responses expose provider_concurrency. Older shared settings seed both provider limits on upgrade; 2 therefore becomes 2 Codex plus 2 Grok workers. The scheduler fills each provider independently, even when the other provider's jobs appear earlier in the queue.


Saga cards now import and render directly, including The Great Work on Urabrask's reverse. Chapter numerals, grouped chapters, reminder/static text, mana symbols and flavour are retained in a dedicated chapter track. Transform cards still produce two independently illustrated faces and paired print outputs. Frame Studio supports Saga previews; new sets require thirteen structures (schema 3), and older frame sets inherit their enchantment styling for Sagas. The 40% height cap and measured 64→36px body fitting apply.


## Verbatim style injection

The effective saved job style is injected unchanged into a delimited style block; agent-authored scene and composition guidance follows in its own block. The provider must run `node studio/art-prompt.mjs REQUEST_JSON SCENE_TEXT OUTPUT_PROMPT_TEXT` and pass the complete assembled text to its image tool. Each newly illustrated face records that file in art_prompt. New and not-yet-started jobs use art_prompt_contract mode verbatim-style-v1. Saved style text is not rewritten or shortened by this formatter. Existing selected reusable Style revisions remain part of the effective style snapshot, with their existing art-technique precedence.

Acceptance verifies the exact block for each new face and saves style-prompt-audit.json. Native Grok image_gen/image_edit input events are also checked when exposed. Codex CLI currently does not expose those image-tool arguments in its JSONL trace, so its audit verifies the agent's saved prompt file and records tool_trace_available=false; this is not a claim of direct tool-input verification. Neither check guarantees the model's visual interpretation or prevents provider-internal prompt processing. Targeted revisions retaining byte-identical prior artwork and local recomposition do not require new image prompts. Original prompt files are copied with recomposed art.

## Chat assistant

The **Chat** button in the top bar opens saved conversations with either the signed-in Codex CLI or Grok CLI. Select a provider when starting a conversation. Each conversation can access all application data or one deck; its scope and permissions remain fixed so changing access starts a fresh conversation. Disable changes for read-only discussions. Generation is a separate permission and is off by default.

The assistant can inspect decks, exact saved prompts, reusable Styles, frame sets, card metadata, version histories, job requests and errors. Image-view tools attach actual saved raw artwork, composed cards or reference images to the selected provider. It can update deck guidelines and card controls, import cards, edit reusable Styles, attach existing artwork as a reference with explicitly selected features, and activate saved card versions. Shared Style changes require all-application scope. Card generation goes through the existing per-deck/provider job queue only when that conversation allows it. Existing queued jobs retain their frozen guidelines.

Access is mediated by a server-side allowlist in `studio/chat.mjs`, not arbitrary SQL or a general terminal. Native CLI shell, filesystem, web, image-generation, subagent and connector tools are disabled/denied for chat; only validated application actions can mutate the library. The CLI runs in an empty temporary working directory and uses subscription authentication, with inference API-key environment variables removed. This is application-level tool isolation, not a separate VM or user account. The CLI process itself still runs as the local account and manages its own subscription credentials.

Messages and tool activity are stored in SQLite (`chat_sessions`, `chat_messages`, `chat_actions`). Mutations retain previous values in `before_json`; the agent can inspect its own prior actions with `get_action` to help undo an edit. Expand **Application activity** to review the calls. Provider attempts and full prompts/results are retained under `library/chats/`. Stop cancels the current turn; completed edits remain committed. Studio restart marks interrupted turns as retryable failures. Chat does not edit application code, delete cards/decks, run arbitrary queries or expose credentials. CLI context is bounded; older messages remain in the database, and large investigations may need a fresh conversation. Grok vision inputs are resized copies to satisfy CLI argument limits; original artwork remains untouched.

The Codex adapter follows the official [non-interactive CLI workflow](https://learn.chatgpt.com/docs/non-interactive-mode) and uses a structured response schema. Both providers use the same audited application-tool loop; there is no provider fallback.

When regenerating an existing card, **Include previous version** is checked by default in the card's Revise panel. Uncheck it for a fresh start: the job excludes the previous version, old prompts/artwork and inherited scene suggestion; artwork from older runs is not supplied as visual reference; new peers from the same generation batch remain available for consistency review. It still uses the current deck guidelines, selected Style/character reference images, exact gameplay data and explicit appearance controls. Old versions remain saved for rollback. The `include_history` choice is frozen in the job request and retained through automatic and manual retries. Appearance-only updates continue to require the existing artwork.

## Generation inputs and filesystem isolation

Every AI card-generation form offers the same input choices: **Include previous artwork**, **Use deck reference images**, and **Isolate generation workspace**. New-deck import and token/basic-land/card-variant forms show the relevant controls when **Generate artwork now** is enabled; they have no prior artwork to include. Per-card generation keeps history and references enabled by default and enables isolation. **Generate missing**, **Generate selected**, **Regenerate all cards**, and manual AI retries open a generation dialog before queueing. The all-card/selected-card dialogs default to **Fresh artwork**, no reference images, and isolation enabled. Choose **Use previous artwork as reference** for continuity, or adjust references and isolation independently. Appearance-only composition does not run an AI and retains its normal workflow.

A fresh style test uses history off, reference images off, and isolation on. Removing text from the deck prompt does not itself remove reference images; the reference checkbox now does. When disabled, reference image files are physically omitted from the job inputs. The setting covers only uploaded deck reference images: web references the written guide asks for, such as an actor's promotional photo for likeness, are still fetched and inspected. Card agents have full internet access (web search, page access and shell downloads). When a card depicts a real person or cast actor, the agent gathers clear face photos, views them, passes them to the image tool as likeness references with the verbatim style text, compares the result against them, and records sources and its likeness check in `data/research.json`. Current written deck guidelines and any pinned reusable Style prompt still apply verbatim. All choices are frozen into `request.json`; automatic retries retain them, and the retry dialog allows changing them for a new request. Old jobs retain their saved choices.

Isolation uses Linux bubblewrap user/PID/mount namespaces. The agent sees `/work`, containing a private copy of the renderer, required fonts, palettes, technical docs and neutral workflow instructions, plus `/work/job` for the current job. The sandbox's root `card-style.txt` is an exact copy of the current job's guide. Only explicitly enabled historical artwork and reference images are copied into this filesystem. The live application project, library, SQLite database, other jobs, user config, conversation memories and past generated-image folders are not mounted. The CLI receives only copied subscription credentials, the image-generation skill, a minimal environment and its own temporary home. Both providers run fresh sessions. Provider files and credentials in that temporary home are removed when the attempt ends; original generated artwork must first be copied into the job, as in the normal workflow. Final composition and validation still run through the trusted host renderer. Virtual output paths are normalized when importing the result.

This is filesystem isolation; networking remains available for provider sign-in, generation and card research. Disabling isolation restores the normal project workspace. If namespace setup or bubblewrap fails, an isolated job fails with an error; it never silently falls back to full project access. Linux/WSL with unprivileged user namespaces and `bubblewrap` is required. Install the distro package (`sudo apt install bubblewrap`), or set `CARD_STUDIO_BWRAP` to its executable. This machine also has a local executable at `~/.local/lib/card-studio/bwrap` from Ubuntu's `bubblewrap_0.6.1-1ubuntu0.3_amd64.deb`. `studio/generation-sandbox.mjs` prepares the allowlisted workspace and mounts; the dependency is checked at job launch.

When a Chat conversation permits card generation, its composer also offers **Card generation inputs**. Those three controls apply to any card jobs queued by the next message and are enforced by the backend, independently of the agent's suggested tool arguments. Conversations without generation permission do not show them.

The sandbox copies the working renderer's Pillow package and its bundled native libraries into a private Python runtime, rather than relying on the distro's older Pillow or mounting the user's site-packages directory. A preflight inside the namespace checks `ImageFont.Layout`, actual Plantin/Beleren text measurements and the mana font before starting the AI provider. Missing renderer dependencies therefore fail before image-generation work begins. The runtime versions and successful font-layout check are recorded in `isolation.json`. Integration tests run both `cardforge check` and `cardforge render` inside the sandbox, as well as the trusted host rebuild.


## Generation batches and commander anchors

Each AI generation submission creates a separate batch. A full-deck regeneration, selected-card run, missing-card run or new-deck/variant submission shares one batch across its jobs, including jobs using different providers. Retries remain in their original batch. A later submission starts a new batch; already existing cards are never implicitly adopted into it. The agent receives only the names/quantities of cards in that submission, not unrelated deck entries. Explicit previous-version and uploaded-reference choices remain separate from peer consistency access.

When the batch includes the deck's commander, it generates first. Partner commanders run in order before other cards. Other workers wait for successful commander completion, rather than using a previous batch's commander. They resume normal parallel generation afterward. If a commander fails or is cancelled, its batch waits until that job is successfully retried; the queue shows **Waiting for commander**. Full-deck runs cannot start a new partial batch while their commander is already generating in a different run. Selected/missing runs do not automatically regenerate a commander that was not selected.

Completed artwork is published atomically to `library/generation-batches/BATCH_ID/`, together with an index of peer version IDs and scene descriptors. The sandbox mounts only its own gallery at `/work/batch`, read-only. The gallery updates while workers are running, so late completions are available at final review. It contains accepted raw illustrations, including both faces where relevant; it contains no peer prompts, old versions, other batches or database. Commander artwork is selected as the preferred visual anchor; otherwise the earliest completed card is the anchor.

Agents run `node studio/batch-consistency.mjs REQUEST_JSON` at the start and again before final visual review, inspect up to three peers and record concrete observations in `batch-consistency-review.json`. The backend checks that reviewed version IDs belong to the same batch. Gallery images are for visual consistency review only, never for direct image-generation conditioning, tracing or artwork reuse. Written guidelines remain authoritative if a peer drifts from them. Scene-diversity checks also use the current batch, including peers completed while another worker was running. Automatic style matching remains an agent judgement; the ID checks verify reference scope, not artistic quality.

### Official Magic printings

Open a card in a deck and choose **Official Magic card** under Artwork source in the Revise tab. This opens a full-page Scryfall browser. Browse all printings and frame treatments, or group by unique illustration; filter the loaded results by set, artist, collector number or frame. English is the default, with an **All languages & exclusive art** option. Load additional pages to search beyond the currently loaded results.

Select a printing to preview its original-resolution scan, then choose **Use this printing**. Double-faced cards save both faces; adventures and other single physical cards save their complete single scan. Scans use Scryfall's PNG when available, with a large JPEG fallback converted losslessly to PNG at its original dimensions. The preview displays native pixels and approximate DPI at 63 × 88 mm; no added detail or higher native resolution is claimed. Many scans are approximately 300 DPI. Official frames, printed names, text and credits remain intact.

The choice is local to this deck entry and becomes a version in its history. Custom versions are preserved. **Custom artwork** restores the latest custom version, or clears the active image ready for a first custom generation. Selecting a historical version also restores that version's source mode. Other decks do not automatically inherit the choice.

Official cards participate in image and print exports, including duplex printing. AI generation and frame recomposition skip cards currently using official scans. Switch them back to custom before asking for a new illustration or custom frame. Downloads and Scryfall catalog pages are cached locally; searches are paced and rate limits produce a cooldown rather than repeated requests. This feature needs internet access, but no Scryfall API key or AI session.

Decklist imports also accept exact printings, for example:

```text
2 x Sol Ring CMM 410
1 Sol Ring (CMM) 703
1 Bala Ged Recovery // Bala Ged Sanctuary [ZNR] 180
3 Forest
```

Set codes plus collector numbers select the exact official printing automatically. The importer accepts optional `x`, parentheses or square brackets around the set, and trailing `*F*`/`*E*` markers (foil markers do not alter the scan). Plain names retain custom-art behavior. The app saves the list immediately and fetches official scans in the background; they appear as each download finishes. Pending imports survive a restart. Missing or mismatched printings show an error and **Retry exact printing import** in the card workshop; they never silently use another printing or generate AI artwork. Printing details are retained in decklist exports. Repeated identical printings de-duplicate; different set/collector combinations stay separate. Name-only re-imports preserve cards already in the deck.

### Artwork sets within a deck

Each deck has one shared card inventory and any number of artwork sets. The **Artwork set** switcher on the deck page swaps the complete editor to that set. Existing decks migrate to **Original artwork**, retaining all saved images, versions, style guidelines and references.

Choose **New artwork set** to start with blank artwork or copy the current images and history. Separately choose a fresh style guide or copy the current guide and reference photos. A fresh guide can be entered directly in the dialog; the usual **Style** page offers the full freeform/structured editor, reusable Styles and reference-image analysis. Copied guides and deck reference records are independent. Each set also keeps its own frame choice, generation provider and per-card customization, notes, approval, scene plans and provider overrides. Use **Rename** to name editions.

All existing card workflows operate on the selected set: generation, revisions, version rollback, choosing official printings, frame composition, review, image downloads and print/export. Version history is scoped to the selected set. Copying a set shares immutable image/version files until new versions are made; later revisions do not change the source set. Generation requests and queue entries record their artwork set. Failed jobs from another set require selecting that set before retrying. Print and ZIP exports use the selected set, with its name in the download filename.

Card names, quantities, sections, role tags and gameplay metadata belong to the deck and remain shared. Adding/removing cards changes the inventory for every set; newly added cards have no art in other sets until generated there. An exact-printing import fills a matching blank shared card in a fresh set instead of adding a duplicate inventory entry. Duplicating a deck copies the selected artwork edition into a separate deck.

Finish or cancel a deck’s queued/running generations before switching sets. Official printing downloads and reference analysis must also finish first. This keeps results attached to the correct set. Set switching saves and restores artwork and guidelines together in one database transaction, and all sets survive application restarts.

**Generate → Populate MTG art** fills blank cards in the selected artwork set with official scans, without running an AI provider. A dialog chooses which printing to prefer: newest (the default), original/oldest, most typical, most unusual, promo, cheapest or most expensive (USD), or avoiding Universes Beyond. These are Scryfall `prefer:` modes. An optional art treatment (borderless, full art, extended art, showcase, retro 1993/1997 frame or textless) narrows the search. When no printing has the treatment, the preferred printing without it is used, then the newest available printing; English scans are tried before other languages. The last choice is remembered in the browser and shown on pending cards in the workshop. Both faces are saved for double-faced cards. Existing images, cards with queued/running generation, and official downloads already in progress are left alone. Failed blank-card imports can be attempted again with this action, or retried individually in the card workshop. Requests persist across restarts; downloads appear live as they complete. Other artwork sets and the shared card inventory are unchanged.

### Printing one card, a selection, or specific pages

Open a card and choose **Print card** in the card workshop header. This prints the exact version currently being previewed, including a historical version, without changing the card’s active version. It starts with one copy regardless of the deck quantity. Adjust the number of copies, paper, card size, margins, crop marks and bleed as needed. Double-faced versions support fronts, backs, or paired duplex pages.

For several cards, check them in the deck viewer and choose **Print selected** in the selection bar, or open the normal **Print PDF** dialog: it starts with those cards selected. The dialog also has **Whole deck / Choose cards**, a searchable checkbox list and Select shown / Clear selection actions. Turn **Include all copies** off for one of each selected card. Explicit selections can include tokens and sideboard cards and are unaffected by unrelated cards without images.

Use **PDF pages** to export a range such as `1, 3-5`; blank means every page. Page numbers refer to the layout after card, quantity and face selection. Fronts and backs are separate PDF pages in duplex mode; a calibration sheet, if enabled, is the last page. The preview shows the first selected page, and only requested pages are included in the PDF. Print at Actual size / 100% and disable Fit to page.

### Outer borders

Choose **More deck actions → Outer borders** to set the selected artwork set’s deck default. A thin black border is the default. Choose a thicker classic black edge, modern lower taper, white/silver/gold colour finish, or **No added border · 0**. Width is adjustable from zero to 2.2 mm at standard card size. Changes save automatically. The dialog previews a custom card from the selected artwork set (preferring the commander or a creature that inherits the deck default), whatever the frame’s border mode. It falls back to a standard bordered reference only when the set has no illustrated custom card, and never uses an official scan as the preview. Expand the reference gallery for other real Magic treatments and official source links.

For an individual card, use **Appearance → Outer border**. **Use deck default** inherits; selecting a style overrides the default on both faces of that card. A per-card zero overrides a nonzero deck default. Border defaults/overrides are independent between artwork sets.

These are reversible delivery finishes. They do not regenerate artwork, move/reflow text, overwrite saved versions, or add footer labels. The viewer, PNG and transparent-frame downloads, ZIP export, and single/selected/full-deck print PDFs use the same cached finished image. Original source masters remain available internally; choosing zero returns the unmodified master. The finish report in `library/border-cache` records source/output hashes and settings.

The modern taper approximates an inward lower-frame flare and protects statistics/loyalty. Official scans always bypass added borders, including borderless printings and explicit card overrides. Their original pixels and dimensions are preserved. Custom-card finishes draw inside the existing canvas; the standard 63.5 × 88.9 mm print size already includes the border. See [the border research report](card-borders-research.md) for treatment distinctions, reference sources and implementation limits.

## Print studio: mix any artwork

Open **Print studio** in the application header to build a persistent print tray independent of deck inventory.

- **Your artwork** browses every deck and artwork set, including inactive sets and archived decks. Filter by deck and custom/official artwork; enable **Include older versions** to browse history. Select individual images or add several selections together.
- **Find real Magic cards** searches Scryfall directly. Enter a card name or Scryfall query (for example `!"Sol Ring"` or `set:lea`). Choose any available printing without adding it to a deck. Both faces of double-faced cards are retained.
- Adjust quantities, remove images or clear the tray. Identical selections merge. The tray persists in SQLite and supports up to 1,000 copies per PDF.
- **Add to print tray** is also available for the selected version in the card workshop and for selected finished cards on a deck page.
- Print uses the same paper, physical dimensions, page range, quality, duplex, spacing, bleed, crop marks and calibration controls as deck printing. Default trim is 63.5 × 88.9 mm including the border. Official scans receive no added border.

Each tray item owns frozen image copies under `library/print-tray/`, together with provenance and the selected artwork set’s border settings. Switching sets, changing deck borders, regenerating a card or deleting its source deck cannot replace that tray image. To print a later appearance, remove the old tray selection and add the intended version again. Deck inventories, active versions and histories are untouched by printing. Removing an item removes its tray record; saved snapshot files remain available for existing export manifests.

The global endpoints are `GET/POST/DELETE /api/print-tray`, `PATCH/DELETE /api/print-tray/:id`, `GET /api/print-library`, `GET /api/print-official`, and `POST /api/print/preview` or `/api/print/pdf`. Preview and PDF accept the same optional `items: [{id, quantity}]` selection; omitted items use the whole tray. These routes retain the app’s local-host and mutation-token protections. Official catalog searches and image downloads use the existing Scryfall gateway, caching and rate limits.


## Native-resolution printing and MTG reconstructions

Production custom masters now render at **1200 PPI (3000 × 4200 px)**. Fonts, symbols and vector frame geometry are drawn at the new resolution; the approved logical layout and physical font sizes remain unchanged. Existing artwork is preserved, including its original resolution limitations. **Details → Print quality** reports master pixels, effective PPI at the standard preset, lettering resolution and saved artwork dimensions.

**Full resolution · preserve source** is the default PDF quality. RGB/sRGB trim-size images can be embedded directly, without creating a second resampled master. PDFs use binary lossless image streams. The 300/600/1200 PPI choices explicitly resample; increasing PPI cannot restore missing source detail. Tagged artwork is normalized to sRGB; printer/paper compensation stays in the printer driver. This is not an automatic paper ICC calibration feature.

The deck menu’s **Refresh custom print quality** rebuilds existing custom art locally as new versions, across that deck’s artwork sets. Select cards first to restrict the refresh. Persistent `quality_jobs` survive restarts, report progress in Print studio, and retain source/target version IDs. The queue publishes atomically and does not change a selection the user has changed during rendering. Official scans are excluded. Earlier versions, saved styles, gameplay, scene metadata, cosmetics and artwork remain intact.

The card workshop distinguishes **Custom artwork**, **Original MTG scan**, and **Reconstructed MTG**. Choose a printing, expand **Reconstruct with sharper text**, and optionally supply higher-resolution official artwork for either face. Reconstruction uses an original bordered template, real fonts/symbols and current English Oracle text, rather than reproducing a printing’s exact original frame or historical wording. Scryfall art crops may be substantially lower resolution than the new lettering; source dimensions are recorded separately. Existing original scans and custom versions remain in history. Supported structures match the renderer: normal cards, tokens, planeswalkers, Sagas, transform/modal double faces, Adventure and preparation; unsupported structures fail without replacing the selected version. Reconstruction is deterministic and uses no AI image generation. **Regenerate all cards** and **Generate selected** skip official and reconstructed cards; **Generate missing** replaces them with custom art.

Print studio also accepts high-resolution full-card image uploads, including downloaded MPCFill files, with an optional reverse face. Imports retain existing lettering and frames, apply no additional border, and belong to the shared print library rather than a deck inventory. The **Existing bleed to remove** control crops declared per-edge bleed before layout (0 for trim-size images; many MPC-ready files use 3.175 mm). Select **Imported high-resolution images** to browse them. PNG/JPEG/WebP inputs up to 16 MB per face and 36 megapixels are normalized to sRGB without enlarging the source.

Deck galleries, covers, stacks, the print-library browser and version strips use separately cached 420-pixel previews. Previews include the selected outer-border finish and never create a large finished-card cache merely to display a thumbnail. Full card inspection, image downloads and printing continue to use the original full-resolution masters. Original scan downloads remain byte-identical to the supplied scans.

## Frame tasks in the generation queue

The generation queue includes a **Frame generation** section with every generated frame revision, including waiting, designing, validation, successful and failed tasks. Progress updates arrive through the same live-update connection as card jobs. **View progress** shows the current phase, complete error and the tail of generation/validation logs; **Open frame** goes to the full editor. The sidebar activity count includes active frame tasks. Worker limits and **Pause cards** apply to card jobs; frame design uses its existing separate worker.

Live editor previews retry temporary busy, restart and connection interruptions. A preview failure is distinct from the saved frame revision’s generation/validation status. Gamba Frame’s saved revision passed validation and remains available. Server shutdown now closes lingering HTTP connections after a bounded grace period so restarts do not leave clients attached to a retired server.
